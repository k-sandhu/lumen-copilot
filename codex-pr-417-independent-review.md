🤖 Codex CLI independent re-review (model gpt-5.6-sol, xhigh) — verdict: needs-changes

This is a retrospective audit of the merged PR. Because ADR-0016/0017/0018 are now Accepted, any correction that changes a decision should land in a new superseding/amending ADR PR, not as an in-place rewrite of these records.

1. **[blocker] `docs/architecture/0017-hierarchical-memory.md` §5 / INV-M3 — “context, not source” is stated but still has no enforcement mechanism.** The current runtime only guarantees that any citation object it creates came from `ToolResult.passages`; it does not verify that each factual claim in the answer is supported, and it can persist non-empty text with zero citations. Putting factual memory in the model-visible `memory` segment therefore lets the model repeat it as an uncited fact despite the prompt and the proposed negative test. A test cannot “block” emission without a defined gate. **Concrete fix:** decide a structural mechanism: either keep factual memory out of final synthesis (use it only to formulate retrieval queries) and limit MVP prompt-visible memory to non-factual preferences/style, or buffer final output behind a claim-to-permitted-passage validator that retries/refuses unsupported claims. Specify the failure behavior and negative tests.

2. **[blocker] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §3.2 — the rolling summary can still launder revoked evidence.** “Conversational content only” can include a prior assistant statement such as “the budget is $5M”; keeping source text out of the summary does not keep source-derived facts out. Rehydrating a separate IDs-only evidence digest and silently dropping revoked IDs leaves that factual summary text in the prompt, where it can be asserted again without a currently permitted citation. Revalidation also names only the requester’s permissions, not the answer’s current effective `collection_ids`/source/mode narrowing. **Concrete fix:** limit the free-text summary to non-factual dialogue state (goals, preferences, unresolved questions), represent every source-derived factual summary item as a claim bound to all supporting evidence IDs, and materialize it only after revalidation through `retrieval/` under the current principal *and effective run scope*. Drop the claim when any required support is unavailable.

3. **[blocker] `docs/architecture/0018-sub-agent-orchestration.md` §3 — a separate worker summary plus evidence list does not preserve INV-3.** The parent is told not to *cite* generated summary text, but it can still repeat facts from that text. If one evidence item is revoked and dropped during parent rehydration, nothing removes the corresponding statement from the worker summary because claims are not bound to evidence. This is the same unsupported-claim channel as memory/session summaries. **Concrete fix:** make the worker return claim-level records (`claim`, `evidence_refs[]`, confidence/coverage), rehydrate all refs first, discard unsupported claims, and give the lead only the surviving claims plus trusted rehydrated passages. Keep any free-form worker summary non-factual/process-only.

4. **[blocker] `docs/architecture/0018-sub-agent-orchestration.md` §5 — the proposed parent FK still cannot work across independent worker transactions.** The current runtime merely mints `assistant_message_id` up front; it inserts the `messages` row after the whole loop, in the parent transaction. `subagent_runs.parent_message_id` therefore still points at a row that does not exist when a worker commits. Saying a stable identity is “created” before dispatch is not enough for an immediate FK, and committing a blank message would introduce a new partial-message lifecycle that the ADR does not decide. **Concrete fix:** introduce a durable `answer_executions`/orchestration row committed before fan-out, make workers FK to that row, and link the eventual `message_id` after successful persistence (or explicitly decide and specify a pre-created message lifecycle, visibility, cleanup, and failure semantics).

5. **[major] `docs/architecture/0018-sub-agent-orchestration.md` §3 — web evidence cannot be rehydrated “through `retrieval/`.”** ADR-0010 makes `retrieval/ → search/` the permissioned corpus path; ADR-0014 and the code make web evidence a distinct `web_search` payload handled through `search_web/` plus the hardened web-fetch path. Routing web URLs through corpus retrieval either violates module ownership or cannot work. **Concrete fix:** define a discriminated parent evidence revalidator: corpus refs go through `retrieval/` with the parent scope; web refs re-check the tenant web-enable, parent knowledge-mode/tool allow-list, and exact fetched snippet provenance through the ADR-0014 path. Decide whether the parent trusts the worker’s content-hashed fetch snapshot or refetches through the SSRF guard, and what happens when content changes or refetch fails.

6. **[major] `docs/architecture/0018-sub-agent-orchestration.md` §4 — `max_tokens` does not enforce the promised aggregate token budget.** Provider `max_tokens` caps completion output, not the worker’s input prompt, tool schemas, retry prompt spend, or fallback attempts. N workers can each stay within their output limit and still exceed the answer/tenant total substantially; the lead’s own input/output reservation is also unspecified. **Concrete fix:** define reservations over total input + completion tokens for every lead/worker attempt. Pre-count the prompt, reserve retry/fallback headroom, derive `max_tokens` from the remaining slice, charge actual reported usage, and charge the full reservation when usage is unavailable. State refund/cancellation rules and make the tenant cap the atomic authority.

7. **[blocker] `docs/architecture/0017-hierarchical-memory.md` §3 — promotion authorization and consent remain undecided for user-authored provenance.** Per-reader document revalidation fixes document access laundering, but a private user utterance has no downstream ACL to revalidate. Merely recording its author as provenance still permits an assistant owner or tenant admin to promote private conversation content to assistant/org scope unless the source user’s consent and the destination approver’s authority are specified. The state-machine fields do not define who may request, approve, deny, or self-approve each transition (INV-5), and singular “a document” language leaves multi-source memories ambiguous. **Concrete fix:** add an authorization matrix per source→destination transition; require explicit source-user consent for any audience widening of user-authored content plus assistant-owner/admin approval for the destination; bind *all* provenance refs into the payload hash; and require all document refs to pass read-time revalidation.

8. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §2.5 — per-answer MCP schema stability conflicts with “revocation always outranks cache stability.”** The real runtime resolves MCP definitions once per answer, and each handler closes over the enabled server/config snapshot. Disabling the server after resolution does not stop an already-advertised call in that answer. Rediscovery on the next answer is not immediate revocation. **Concrete fix:** keep the advertised schema snapshot stable for caching, but require an invocation-time tenant/owner/`enabled`/policy recheck before every outbound MCP call; a revoked tool returns a typed denial without contacting the server. Add a disable-between-dispatch-and-invoke negative test.

9. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §§1, 3.1 — budgeting is explicitly pre-first-call, but the transcript grows before every later model call.** `ToolResult.content` is unbounded relative to the initial prompt, and the current loop appends it before resending the full transcript. §3.1 names later compaction but never makes a per-turn preflight guard a prerequisite, so #410 can satisfy the written first-call budget and still hit provider context errors before #415 lands. The later #410 implementation in this checkout in fact needed a follow-up per-turn guard, demonstrating the ambiguity. **Concrete fix:** require the same budget check before *every* completion, retry, fallback, continuation, and worker call; trim allowed history, invoke §3.1 compaction when the protected live tail crosses threshold, then produce the typed refusal if it still cannot fit.

10. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §1 — a 100k default is not a conservative unknown-model fallback.** Lumen explicitly supports custom OpenAI-compatible routes; an unknown local/custom model may have a 4k/8k window. Budgeting it as 100k reintroduces the reactive provider `ContextWindowExceeded` that this ADR claims to eliminate and is not LLM-agnostic fail-safe behavior. **Concrete fix:** require an explicit context-window value when registering an unknown route, or use a genuinely safe floor no larger than the smallest supported model. Treat missing metadata as configuration/typed refusal rather than assuming 100k.

11. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §§4, 6 — the narration classification point is still load-bearing and unspecified.** The current runtime buffers a whole turn because text arrives before it knows whether tool calls follow. Emitting every text delta immediately as `event:narration` would misclassify a tool-free final answer; waiting for the terminal would not be live. It also determines exactly when retries become forbidden. `event:narration` is absent from the current WS schema/vocabulary. **Concrete fix:** specify: buffer text until the first tool-call fragment; when tool intent is known, flush it as narration and atomically close the retry window; if the turn terminates tool-free, emit it as answer deltas. Freeze the additive narration payload contract first and test text-before-tool, text-only, fault-before-flush, and fault-after-flush cases.

12. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §5 — the concurrent-tool persistence design assigns ownership twice.** It says each isolated call scope has its own repository/audit/approval handles, then says a serialized coordinator on the runtime session writes `tool_invocations` and audit events. The real `ToolRunner` currently audits and records inside `run()` and allocates the ordinal in `_finalise`, so applying both statements either duplicates writes or still orders by completion. Transaction behavior when the parent answer fails is also not decided. **Concrete fix:** choose one owner. Prefer factoring execution/governance from persistence: preassign the ordinal at dispatch, return a typed invocation record, and make the coordinator the sole audit/trace writer with explicit commit/rollback durability. Alternatively let call sessions commit independently and define logical ordering by the preassigned ordinal; do not prescribe both.

13. **[major] `docs/architecture/0017-hierarchical-memory.md` §2 — “existing OpenSearch family” does not decide the index topology or the citation firewall.** ADR-0010 chose one shared chunk index and current hydration produces `RetrievedPassage`. Memory needs a different domain result because it is explicitly not a citation source. A second memory index changes ADR-0010’s topology; mixing memory documents into the shared index without a mandatory corpus discriminator risks ordinary retrieval hydrating memory as a passage/citation. **Concrete fix:** decide one of: (a) the same index with a mandatory `corpus_kind` filter in both document and memory query builders plus a distinct `MemoryHit` hydration type, or (b) a second index via an explicit ADR-0010 amendment. Add negative tests proving document retrieval/citation paths can never return a memory entry.

14. **[major] `docs/architecture/0016-context-engine-and-cache-first-prompting.md` §2.4 — the capability-map placement contradicts its own boundary promise.** The ADR says provider capability knowledge stays inside `llm/`, but also says `ModelRoute` grows an `anthropic-style`/`openai-style` capability. In the actual code `ModelRoute` lives in `services/provider_models.py` and is carried by `chat_runtime`, so that change exports provider-specific cache semantics above the gateway. **Concrete fix:** keep the route descriptor above `llm/` provider-neutral and resolve cache behavior entirely inside the gateway from an opaque route/provider identifier; otherwise explicitly move/redefine the type at the domain/gateway boundary without exposing provider categories to services.

15. **[minor] ADR-0016/0017/0018 headers — the “amended before first merge” wording invents an immutability boundary ADR-0001 does not state.** All three files were already marked `Accepted` in the first commit, and ADR-0001 says “Accepted ADRs are immutable,” not “merged Accepted ADRs.” The amended headers therefore rationalize an undocumented exception. The Nygard structure, numbering, index entries, and issue links otherwise match house style. **Concrete fix:** use `Proposed` through review and switch to `Accepted` only in the final pre-merge commit in future; now that these are merged, record substantive corrections in a new superseding/amending ADR PR.

The second pass did verify that many first-review amendments are real: `context_digest` is now explicitly distinct from the user-facing `ToolResult.summary`; the LiteLLM 1.55.9 upgrade is a named #411 prerequisite; retryability, fallback validation, and `tool_choice="none"` continuation are specified; `PolicyApprovalGate` is correctly rejected for memory promotion; document-backed promoted memory is read-time revalidated per reader; `WorkerScope` explicitly carries the parent’s narrowed `collection_ids`; and `RunTranscriptSink` buffering is correctly recognized as insufficient for incremental worker persistence. The findings above are the remaining load-bearing gaps.
