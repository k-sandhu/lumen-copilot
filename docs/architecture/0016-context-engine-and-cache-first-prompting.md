# 16. Context engine & cache-first prompting (the runtime performance track)

- **Status:** Accepted *(direction approved by the sponsor in-session 2026-07-16; amended same day for the [#417 review](https://github.com/k-sandhu/lumen-copilot/pull/417) findings before first merge — an accepted ADR is immutable thereafter; changes supersede)*
- **Date:** 2026-07-16
- **Builds on:** [ADR-0003](0003-application-stack.md) (LLM-agnostic; every model call via the `llm/` gateway), [ADR-0004](0004-architecture-boundaries-and-adapters.md) (one owning module per concern; domain types only), [ADR-0011](0011-assistant-and-agent-runtime.md) (one shared `chat_runtime`), [spec 0004](../specs/0004-security-and-domain-invariants.md) (INV-2 permissioned retrieval, INV-3 citations, INV-6 audit)
- **Scope:** SPIKE — the only deliverable of [#405](https://github.com/k-sandhu/lumen-copilot/issues/405); no product code. Guidance for [epic #404](https://github.com/k-sandhu/lumen-copilot/issues/404) ([#409](https://github.com/k-sandhu/lumen-copilot/issues/409)–[#416](https://github.com/k-sandhu/lumen-copilot/issues/416)). [ADR-0017](0017-hierarchical-memory.md) and [ADR-0018](0018-sub-agent-orchestration.md) build on the segments and executor decided here.

## Context

The answer path is *bounded but count-based and cache-unaware*. Precisely (naming the actual owners):

- **History selection** is a fixed 20-message slice in `chat_service` (`_HISTORY_TURNS`), projected **text-only** in the API layer (`api/v1/chat._to_chat_messages`); the runtime (`chat_runtime._answer`) then builds `[system, *history, question]` with **no token accounting anywhere**. An oversize prompt fails *reactively* as the provider's `ContextWindowExceeded` → 422. Prior turns' tool evidence is dropped entirely.
- **No completion-side caching.** One answer runs up to 20 sequential completion turns, each re-sending the full prefix (tool specs + system + history + growing tool transcript) with no cache directives and no `prompt_cache_key`. (A *query-embedding* LRU cache exists — #395 — that is retrieval-side and unrelated.)
- **Tool calls execute sequentially** even though the gateway already parses parallel tool-call fragments.
- **A transient provider fault mid-answer kills the whole answer**; `finish_reason == "length"` is unhandled; no fallback model (routing/fallback was fenced out of #25 — this ADR closes that at the *turn* level).
- **Pre-tool narration is dropped** (the #148 fix), so nothing streams until a whole turn completes.

Provider state (2026-07, links current as of writing): OpenAI-style caching is automatic on stable ≥1024-token prefixes with a `prompt_cache_key` routing hint ([OpenAI prompt-caching guide](https://developers.openai.com/api/docs/guides/prompt-caching)); Anthropic-style caching is explicit `cache_control` breakpoints ([Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching); ~1.25× write, ~0.1× read pricing). LiteLLM passes both through and (in versions **later than our pinned 1.55.9**) can auto-inject breakpoints via `cache_control_injection_points` ([LiteLLM PR #9996](https://github.com/BerriAI/litellm/pull/9996)) — see §2.4's prerequisite. Published external results (e.g. Anthropic's [context-editing benchmark](https://platform.claude.com/docs/en/build-with-claude/context-editing), 84% token savings on a 100-turn task) are **external references, not Lumen guarantees**; our targets live in Consequences with their acceptance gates.

These are one design problem: caching, compression, and (later) memory constrain each other through **prefix stability** — a sliding per-message window invalidates the cache every turn; a mid-answer memory write invalidates everything after it. The consensus architecture is a deliberate context assembler with a stability gradient; this ADR adopts it.

## Decision

### 1. A segmented, token-budgeted context assembler owned by `llm/`

A new `backend/app/llm/context.py` (prompt assembly is part of the model boundary — no new AGENTS.md §6 row) owns turning the run's inputs into the message list, as ordered **segments with a stability gradient**:

| # | Segment | Content | Stability |
|---|---|---|---|
| 1 | `tools` | Advertised tool specs (deterministically sorted) | Per allow-list |
| 2 | `system` | user custom instructions → assistant instructions → grounded prompt | Per session |
| 3 | `memory` | **Reserved, empty in v1** (ADR-0017); changes only between answers | Semi-stable |
| 4 | `summary` | **Reserved in v1** (§3.2); versioned; changes only between answers | Semi-stable |
| 5 | `history` | Verbatim recent turns, token-budgeted | Rolls at answer boundaries |
| 6 | `live` | Question + this answer's growing tool transcript | Append-only in-answer |

**Budget mechanics (the `ContextBudget` contract):**

- `input_budget = max_input_tokens(model) − output_headroom − safety_margin`. `max_input_tokens` resolves via the local model map; an **unknown model uses a configured conservative fallback** (`Settings`, default 100k) — never a crash (#410 AC-3). Headroom and fallback are `Settings`-tunable.
- Counting: an injectable token-counter seam (default: LiteLLM tokenizer, lazily imported; heuristic fallback for unknown tokenizers) counts **system, question, history messages (plus a fixed per-message overhead), and the serialized tool schemas** — tool specs ride the `tools` param but spend the same window. A fixed safety margin absorbs local-vs-provider tokenizer drift.
- **Degrade order, applied *before* the first model call:** shrink the memory segment → roll history into the summary → drop oldest history messages → **typed refusal**: a prompt whose *fixed* segments (system + tools + question + headroom) cannot fit raises `ValidationError` (`context_too_large`, 422), mapped to the terminal problem envelope. Retrieval-side budgets (`default_k`, snippet caps) are **derived at context-build time and passed into the run's `ToolContext`** — the assembler never "shrinks k retroactively"; it sets the knobs before any tool executes.
- Required tests: unknown model → fallback; deterministic assembly; oldest-first trimming; oversized tool schemas; the typed refusal; tokenizer-variance tolerance.

### 2. Cache-first prompting rules

1. **Stable prefix ordering** (the table above); volatile content only at the tail; deterministic serialization (sorted tool specs, stable JSON key order, no timestamps in segments 1–4).
2. **Append-only within an answer** (already true) — except §3.1's *chunked* compaction, threshold-triggered to amortize invalidation.
3. **Trim only at answer boundaries, in chunks** (roll K turns at once).
4. **Breakpoints & routing hints (amended by [#448](https://github.com/k-sandhu/lumen-copilot/pull/448), implementing [#411](https://github.com/k-sandhu/lumen-copilot/issues/411)):** the LiteLLM upgrade originally named as a prerequisite is **withdrawn — the pin (1.55.9) stays**. Validation showed both directive shapes are pure pass-through on the pinned version's OpenRouter adapter: `cache_control` content-parts ride the message list unmodified and `extra_body.prompt_cache_key` rides the request body (live-verified against a real Anthropic route: nonzero cache reads on turn 2). The gateway therefore decorates the serialized wire itself, post-`_to_wire_messages`; `cache_control_injection_points` is re-evaluated whenever LiteLLM is next upgraded, not before. The **route-capability map lives inside `llm/`, keyed off the resolved route the gateway already receives per call — (model id, api_base)**. Directives are granted **only to routes demonstrably going through OpenRouter** — the one transport the pass-through was validated against: a given `api_base` must BE the OpenRouter host, and a no-base id must carry the `openrouter/` adapter prefix (a registry id like `anthropic/claude-…` without it routes through a native LiteLLM adapter that was never validated → nothing). Within an OpenRouter route the family is the **upstream provider PREFIX of the raw id** — the namespace OpenRouter itself routes by, never a substring of the model name: `anthropic/…` → an explicit `cache_control` mark on the stable prefix boundary (message 0) plus a **moving mark on the last cacheable block** (each call writes its full prefix; the next append-only call reads it); `openai/…` → no marks, pass `prompt_cache_key=session_id`; every other upstream, every other adapter, and **any custom `api_base`** → **omit every cache directive, fail-safe** — a route's model NAME never earns directives its TRANSPORT wasn't proven to accept. `ModelRoute` stays capability-free: duplicating the capability above `llm/` would leak provider categories into `services/`; the gateway is the single resolver. Each category keeps a gateway *payload* test (decorated, steered, bare). The kill-switch `CHAT_PROMPT_CACHE_ENABLED` is process-static (read at startup).
5. **Mask, don't remove, tools — per-ANSWER stability:** the offered set is stable within an answer by construction (resolved once). Across answers, MCP **rediscovery rewrites `discovered_tools` and can change schemas/order mid-session** — accepted: correctness and **security revocation always outrank cache stability** (a disabled server's tools vanish immediately, ADR-0012); the cost of a rediscovery is one prefix invalidation. A per-session pinned tool manifest was considered and rejected for v1 (staleness risk over cache micro-savings).
6. **Measure it** — §2.6.

Recorded semantic decision: the existing instruction order (user → assistant → grounding) is kept; cross-user prefix sharing is deliberately not optimized. Revisit only with eval evidence.

### 2.6 Usage accounting (the substrate — [#409](https://github.com/k-sandhu/lumen-copilot/issues/409))

`TokenUsage` gains `cached_prompt_tokens` / `cache_write_tokens`; the `done` envelope reports them (additive contract fields); the tenant-scoped **`llm_usage` table is the accounting ledger**. Granularity: **one row per (answer, model-route attempt-scope)** — with today's single-model no-retry loop that is exactly one row per answer, keyed by `message_id`. When §4 retries/fallback and ADR-0018 workers land, **additional rows** attribute those spends: each row's `model` is the model *actually used*; fallback-attempt and worker rows carry `message_id` NULL and key by `run_id`/worker identity; per-answer totals are aggregations over the ledger. The uniqueness guard is therefore **partial — one row per non-null `message_id`**. Terminal audit events record the actually-used model whenever it differs from the requested one.

**Amendment ([#490](https://github.com/k-sandhu/lumen-copilot/issues/490) / R2-3, 2026-07-24) — the post-terminal follow-up-suggestions call is attributed to the model that ran it, not to the answer model.** Since #490 the suggestions nicety can run on a *dedicated* (fast) model distinct from the answer's route, so actual-model attribution requires its own row: the suggestion spend is an **additional** message-less scope (`message_id` NULL), `model` = the actual suggestions model, grouped by the answer (`answer_id` + `session_id`) and tagged `run_id = answer_id` so it is at most one per answer (recorded **idempotently** — a repeated post-terminal application is a no-op) and distinguishable from §4 failover scopes. It is **not** folded onto the answer's `message_id`-keyed row, which would misattribute the spend to a model that did not incur it. It is recorded whether or not the completion parses into suggestions (the tokens were billed regardless), and `COUNT(message_id)` still excludes it — a suggestions call is not an extra "answer". This supersedes #489's original one-row wording, which assumed the pre-#490 world where suggestions rode the answer's own route. `done.usage` remains answer-only.

### 3. Compression (three timescales)

**3.1 In-answer tool-result compaction ([#415](https://github.com/k-sandhu/lumen-copilot/issues/415)).** When the live transcript crosses a budget threshold, the **oldest** tool results' contents are replaced by a placeholder, cleared in **chunks** to amortize cache invalidation. The placeholder is a **`context_digest`: a bounded, content-bearing extract produced from the result's actual content at clearing time** — NOT the user-facing `summary` (an optional ≤300-char count-style line; "3 passages" is not evidence and must never be all the model is left with). Constraints: results whose passages the answer **already cited** keep the cited snippets verbatim in the digest; the compression-regression eval (§3.2) must prove post-compaction answers stay grounded (INV-3).

**Amendment ([#491](https://github.com/k-sandhu/lumen-copilot/issues/491), 2026-07-23) — compaction also fires PROACTIVELY, not only over budget.** The budget-threshold trigger above never fires on a frontier-sized window, so a superseded search result rode every later turn at full size — the re-sent-evidence tax #491 measured (~5,400 of ~11,060 cumulative input tokens on a 3-tool answer). `fit_transcript` now runs a **budget-independent** pass that digests a tool result once it is **both** (a) *superseded* — a later tool-call group exists in the live tail — **and** (b) *represented in citations* — its `tool_call_id` is in `cited_snippets`, so its evidence is durably recorded (INV-3) and re-fetchable by id. Two invariants make it safe and preserve §2's prefix stability: the **newest tool-call group is never touched** (the evidence a *pending* tool call is about to reference stays verbatim — #491 AC-6), and the same **strict cost-reduction guard** as the reactive path applies, so a result already at/under the cap is left verbatim (idempotent across turns → the cache prefix does not churn). The proactive digest is the bounded content-bearing **head** (leading passage id labels survive, so references can be re-fetched) + each **cited snippet re-embedded verbatim** + the truncation marker — the same `context_digest` the reactive path builds (the amendment below corrects an earlier claim that the proactive path did *not* re-embed cited snippets). Configurable and **off in the pure assembler** (`ContextConfig.proactive_compaction_enabled=False`); the chat answer path opts in via `Settings.context_proactive_compaction_enabled` (default on), with the retained-**head** cap reusing `CONTEXT_COMPACTION_DIGEST_CHARS`. Groundedness under proactive compaction is guarded by the same compression-regression eval (§3.2 / OD-7 lane).

**Amendment ([#491](https://github.com/k-sandhu/lumen-copilot/issues/491) BE-2 / R2-9, 2026-07-24) — proactive compaction re-embeds cited snippets verbatim (INV-3).** The #491 amendment above originally specified that the proactive digest kept only the head + marker and did **not** re-embed cited snippets, reasoning that a superseded result's evidence already lived in the citation records. That is a defect against **INV-3: a citation must resolve to evidence the model actually saw in the prompt**, not merely to a record kept elsewhere — a cited passage sitting *beyond* the retained head would be truncated out of the model-visible transcript while a citation still pointed at it. The proactive path therefore builds the **same `context_digest` as the reactive path** — head + every cited snippet re-embedded **verbatim** + marker (`_context_digest` given the call's `cited_snippets`) — so a compacted result's cited evidence stays visible to the synthesizing model. The **strict cost-reduction guard** is unchanged and per-result: when keeping the verbatim snippet cannot shrink the message, it is left **verbatim** (evidence is never traded for a shrink, and the idempotence → prefix-stability property still holds). Because the marker and the re-embedded snippets have their own cost, the digest is *not guaranteed shorter* than the input — which is exactly why the cost guard gates every mutation; `CONTEXT_COMPACTION_DIGEST_CHARS` bounds only the **head**. This supersedes the "does not re-embed" wording above; groundedness stays gated by the compression-regression eval (§3.2).

**3.2 Rolling session summary + token window + evidence carry-forward ([#416](https://github.com/k-sandhu/lumen-copilot/issues/416)).**

- `session_summaries` is a **tenant-scoped table like every other** (`tenant_id` FK + the fail-closed RLS backstop; owner scoping via the session's owner), updated asynchronously post-answer under a **tenant-bound Celery scope** (the ADR-0015 pattern). Assembly consumes `[summary vN] + [last M turns verbatim]`, M token-budgeted — replacing `_HISTORY_TURNS`.
- **Summaries carry conversational content only — never source-document text.** The **evidence digest is IDs only** (document + chunk ids); the next answer **rehydrates them through `retrieval/` under the requester's *current* permissions** (INV-2 — "the user saw it last turn" does not prove they may see it now; revoked/deleted evidence is silently stripped). Summarization and evidence rehydration emit audit events (INV-6).
- Summarizer failure degrades to the verbatim window; never a failed answer.
- The eval harness gains the compression-regression suite (golden multi-turn conversations; groundedness/citation thresholds hold under compaction).

**Amendment ([#491](https://github.com/k-sandhu/lumen-copilot/issues/491), 2026-07-23) — the verbatim-tail / min-batch defaults are retuned to summarise EARLIER.** The rolling summary only begins folding turns once `keep_messages + min_batch` messages have accumulated. The original `8 + 4 = 12` meant the first compaction fired at ~turn 7 of a 2-message/turn session, by which point turn-5 input was already ~2.5× turn-1. Retuned to `4 + 2 = 6` (first compaction ~turn 3): the verbatim tail still carries the last **2 full turns** word-for-word (the immediate context the model most needs), and older turns roll into the ≤300-word summary + IDs-only evidence carry-forward. These are `Settings` defaults (`CHAT_SUMMARY_KEEP_MESSAGES` / `CHAT_SUMMARY_MIN_BATCH`), not values this ADR pins, so the retune is a default change, not a decision reversal — the §3.2 mechanism (summary + M-turn verbatim tail, evidence-ids-only carry-forward, forward-only coverage) is unchanged. The summariser runs on the dedicated FAST model (#490), so the earlier/smaller batches cost little; groundedness under the shorter tail stays gated by the compression-regression eval above.

**3.3 Recall — compaction is now reversible ON DEMAND ([#569](https://github.com/k-sandhu/lumen-copilot/issues/569), epic #533 R1, 2026-08-06).** §3.2 makes the model's view of a conversation *lossy by design*, and the #491 retune above made it lossy **sooner** — first compaction at ~turn 3. The summary is a good default and a bad floor: "as we discussed earlier" resolves to a paraphrase at best, and to nothing at all once the detail falls out of the ≤300-word budget. The transcript itself was never lost — `messages` is append-only and the *user* reads it through `GET /chat/sessions/{id}/messages` — so this adds the missing **function** rather than a second store: the T0, read-only `read_conversation` tool, which the model calls when it chooses to.

Four constraints keep it from undoing the sections above:

- **Bounded to the compacted range**, defined as the exact set-complement of the live window's predicate (`MessageRepository.search_for_session_before` ↔ `list_for_session_after`). The two partition the session, so recall can never return a turn already sitting verbatim in the prompt — no budget is spent restating context.
- **It carries no passages**, so it never enters `cited_snippets` and therefore lands in §3.1's **tier 1** — the first thing digested under pressure. Recall is navigation; evidence outranks it, and the degrade order is preserved rather than inverted.
- **It contributes no citations.** There is no `conversation` citation kind and this deliberately does not invent one: `citations.chunk_id` is a NOT NULL FK to `chunks` and INV-3 says a citation resolves to a permitted passage the model actually read. To quote anything recalled, the model re-retrieves it. INV-3 is unchanged.
- **Recalled evidence is re-checked, not replayed.** A stored assistant turn quotes documents inline, so an old turn can carry text whose grant was since revoked — the §3.2 rule ("the user saw it last turn does not prove they may see it now") applied to prose instead of to ids. Cited document ids ride back from the seam and go through the same `retrieval/` chokepoint the evidence carry-forward uses; a turn with any no-longer-permitted citation is **withheld whole**, since a quotation cannot be reliably excised from prose.

A **per-answer call budget** and a repeat-query short-circuit live in the seam, not in the tool's description — a bound the model is asked to respect is a suggestion.

### 4. Turn-level resilience ([#413](https://github.com/k-sandhu/lumen-copilot/issues/413))

- **Retryability is classified, not blanket:** the gateway (the only reader of vendor exceptions) maps provider failures to typed categories — `retryable` (timeout, connection, 429 with backoff honoring `Retry-After`, provider 5xx) vs `terminal` (auth/permission, malformed request, unknown model, configuration). Only `retryable` faults retry (≤2, backoff); auth/config faults fail fast exactly as today.
- **The retry window closes at first emission:** a turn retries **only if nothing of it has been published**. Narration streams live (§6), so a turn that already emitted narration is not retried — a fault after emission ends the answer with the typed terminal, exactly as today. Tool side effects run between turns, so a retry can never re-execute a tool.
- **Fallback models are a defined, validated configuration** (new in #413): an ordered per-tenant list of model ids, each validated against the tenant's provider config exactly like the primary (the send-path rules), resolved to routes once, keys via the existing PR-2a path. `done` + audit record the model actually used; its `llm_usage` row attributes the spend (§2.6).
- **Length continuation:** on `finish_reason == "length"`, the buffered partial text is appended to the transcript as the assistant turn and **one** continuation turn runs with `tool_choice="none"` — a continuation can never re-issue tool calls, so duplicate tool execution is structurally impossible; the streamed answer is the concatenation.

### 5. Concurrent tool execution ([#412](https://github.com/k-sandhu/lumen-copilot/issues/412))

- The calls of one turn run under `asyncio.gather` with a small semaphore. **Ordinals are preassigned at dispatch** (the runner's counter moves to dispatch time); `tool_call` events emit at dispatch, `tool_result` events on completion; transcript messages append in **original call order**.
- **Per-call isolation is a context, not just a session:** `ToolContext` gains a factory yielding, per concurrent call, a **fully isolated call scope** — its own `AsyncSession` (tenant-bound via `bind_tenant`, RLS-armed), its own `RetrievalService`, and its own repository/audit/approval-gate handles. Completed results queue into a **serialized persistence coordinator** (the runtime session) that writes `tool_invocations` rows and audit events in dispatch order — the INV-6 trace stays gap-free under parallelism.
- v1 conservatism: read-only T0 calls run concurrently; T1+ calls in the same batch run serially after them. Required tests: parallel RLS isolation, audit completeness, ordinal order, hanging-call timeout containment, mid-batch failure, rollback behavior.

### 6. Narration streaming ([#414](https://github.com/k-sandhu/lumen-copilot/issues/414)) — named `event:narration`

A tool-calling turn's text streams live as **`event:narration`** (not "thinking": this is the model's ordinary *visible* narration text; **provider hidden-reasoning blocks are explicitly excluded** — never requested, never forwarded). Never a `delta`, never persisted — the #148 invariant (streamed answer == stored message) holds. The §4 interaction is explicit: narration emission **closes the turn's retry window**; replays (the Redis buffer) re-deliver narration envelopes idempotently by `seq` like every other event, rendered as transient status — no user-visible duplication.

**The classification point (amended per #427 item 11): buffer-until-first-tool-fragment.** A turn's streamed text is BUFFERED until the stream carries its **first tool-call fragment** — the earliest moment the turn is provably tool-calling, hence its text provably narration rather than answer. At that moment the buffered text **flushes as `event:narration`** (subsequent turn text streams as narration live) and the turn's **retry window closes** (§4: a turn that emitted anything is never retried or failed-over — the fault becomes the typed terminal). A turn that ends with **no** tool-call fragment stays fully buffered and is the answer (or the `ask_user` question), published exactly as before — the answer path's buffering is untouched. Consequences of this point, stated: providers that only reveal tool calls at stream end flush the narration just before the `tool_call` events (still ahead of them on the wire); the narration of a turn whose batch is later discarded (`ask_user` interception, spec 0006) has already streamed and stays what it is — transient status.

**The frozen additive payload** (`contracts/websocket-envelopes.schema.json`, `ChatNarration`): `event` envelopes with `name: "narration"` and `data: { "text": string, "turn": integer ≥ 1 }` — `text` is one narration chunk (append-ordered within the turn by `seq`), `turn` the 1-based answer-loop turn it belongs to (clients reset the transient display per turn). Additive and optional: clients ignoring `narration` events lose nothing but liveness.

**Amendment ([#487](https://github.com/k-sandhu/lumen-copilot/issues/487), 2026-07-23) — streamed text is coalesced, so `text` is *one or more* chunks.** The producer no longer mints one envelope per provider chunk (that made envelope count track the provider's tokenisation, and every envelope cost a backplane round-trip). Adjacent chunks of the **same kind** — answer `delta`, or one turn's `narration` — are buffered and flushed on whichever comes first, a character budget or an elapsed-time deadline (`CHAT_TEXT_COALESCE_CHARS` / `CHAT_TEXT_COALESCE_SECONDS`; `0` chars restores the pre-#487 one-envelope-per-chunk shape). Two rules make it safe: kinds never merge (answer text can still never appear inside a `narration`, so the #148 invariant is structural), and the buffer is flushed **unconditionally before any other envelope is minted** — so `seq` stays monotonic *on the wire* and no text can be stranded behind a terminal. Coalescing changes envelope COUNT, never TEXT. Placement is deliberate: the seam is envelope construction in the runtime, never `RedisBackplane.publish`, so the bounded replay list and the live channel keep carrying byte-identical envelopes (#153) — and the smaller envelope count is what keeps a long answer inside the 512-envelope replay window.

**Amendment ([#488](https://github.com/k-sandhu/lumen-copilot/issues/488), 2026-07-23) — the answer turn streams speculatively; the classification point stops being "buffer the whole turn".** The buffer-until-first-tool-fragment rule above made *time-to-first-answer-token equal to the whole synthesis turn* — the single largest chat-latency contributor (#486). #488 narrows the buffering to only what correctness requires, in two tiers, preserving the #148 invariant in its retraction-aware form: **the persisted assistant message equals the concatenation of delivered-and-not-retracted answer `delta`s.**

- **Tier (a) — tool call impossible → stream live unconditionally.** When a turn cannot call a tool — the forced tool-free synthesis (`tool_choice="none"`) and any turn entered with an empty tool list — its text is streamed live as answer `delta`s with no speculation and no ambiguity. This alone captures the forced-synthesis path (the empty-answer #148 fix path).
- **Tier (b) — speculative streaming with a defined retraction.** When tools ARE advertised (`tool_choice` auto), the turn's text streams live as answer `delta`s *before* the turn is proven tool-free. The classification point is unchanged (the first tool-call fragment, §6 above / #414); if it fires, the runtime publishes **`event:answer_retract`** — a whole-turn retraction (contract: "discard every answer `delta` of the currently streaming turn") — then re-emits the buffered text as `event:narration` and narrates the rest live, exactly as before. The retraction is well-defined because **at most one un-finalised speculative block exists at any instant** (a tool-free turn ends the answer, so no speculation ever follows a finalised block).

**The §4 retry-window interaction, resolved by the retraction (not by closing the window).** §4's window closes at first *narration* emission, because wire output cannot be duplicated by a retry. Speculative answer `delta`s are also wire output, but — unlike narration — they can be **un-published**: on a retryable fault (or before a failover) the runtime emits `answer_retract` to undo the current turn's speculative deltas, then retries/fails-over cleanly. So live answer streaming does **not** close the retry window; the window still closes only at narration (a genuinely committed transient emission). A *non-retryable* fault mid-speculation still ends the answer with the typed terminal (the client discards the whole stream on `error`, as for narration).

- **The length continuation stays buffered (tier neither).** The one continuation turn (`finish_reason == "length"`, §4) runs *after* a finalised answer block, so a whole-turn `answer_retract` there would wrongly discard the finalised partial too. It therefore keeps the pre-#488 buffered shape (published after it completes) — which also keeps the "at most one un-finalised speculative block" invariant true. The continuation is a bounded tail; buffering it costs no time-to-first-token (the main turn already streamed).
- **`max_tokens` on the answer/synthesis call (`CHAT_ANSWER_MAX_TOKENS`, threaded through `stream_tools`).** Answer length — and therefore the tail of the wait — is now bounded; `finish_reason == "length"` becomes an ordinary terminal handled by the one continuation (capping a single answer at ~2× the value). `0`/unset ⇒ unbounded (the pre-#488 shape; the offline/headless default).

## Consequences

- **Targets, each with a gate** (not guarantees): tool-heavy input-cost reduction ~50–80% — *measured by the §2.6 cache-hit KPI on a fixed golden workload before/after #411*; multi-call tool latency approaching max-of-latencies — *the #412 test workload*; zero context-window 422s on golden conversations — *the #410/#416 suites*.
