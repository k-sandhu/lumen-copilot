Executive verdict

“Slow” is four stacked problems—not one FastAPI problem

Environment invalid

Worktrees share a Compose identity and data volumes

Current containers and persistent data came from different checkouts. The database revision is orphaned relative to the current migration chain, while liveness stays green.

Developer tax

Perceived latency

Answer “streaming” waits for a full model turn

The runtime buffers tool-free answer chunks until the provider finishes, then emits them. Time-to-first-visible-answer is therefore close to full-turn latency.

Tail amplification

Remote models, tools, retries, and resource churn multiply

Confirmed contributor

One verify occupies the event loop

Argon2’s cost is intentional security work. The problem is executing it on the single reload worker’s event-loop thread.

  • Concurrent lightweight requests pause behind it.
  • Unknown-user dummy verify has the same cost by design.
  • A bounded thread/process execution seam preserves timing uniformity without blocking the loop.

Search critical path

Search serializes six latency domains into one REST response

1 · Record recent query (Postgres)A write enters the request transaction before retrieval.
2 · Resolve per-user grants (Postgres)Builds the permission filter fresh so revoked access disappears immediately.
3 · Embed query (external provider)Remote call; cached only for repeated single-query, tenant-namespaced inputs.
4 · Ensure index + hybrid search (OpenSearch)First process search also pays one index/pipeline check.
5 · Hydrate and re-check passages (Postgres)Defense-in-depth query plus document metadata enrichment.
6 · Generate optional direct answer (external model)Route passes no opt-out, so results wait for up to a 300-token completion when the gateway is enabled.
7 · Audit + commit (Postgres)The response is not released until the full transaction commits.
backend search.py, search_service.py, retrieval/service.py, LLM gateway, OpenSearch store.
13

Search amplification

Correctness checks also create avoidable query and tail latency

Per-document enrichment

Results loop over passages and await DocumentRepository.get once per distinct document. The cache avoids per-chunk queries, but a 20-document page still adds ~20 serialized reads.

Direct answer blocks results

The synthesized answer is described as optional, but there is no request parameter to skip it. A slow provider delays already-available ranked passages.

Transaction spans the waterfall

The request-scoped SQLAlchemy session remains active while embedding, OpenSearch, and model I/O occur before commit.

T(search) ≈ T(grants) + T(embed) + T(OpenSearch) + T(hydrate) + Ndocs·T(meta) + T(answer) + T(commit)

Design direction: return ranked results first; bulk-enrich metadata; synthesize the cited answer as a separately budgeted, cancellable phase.

Static critical-path trace. Exact component shares require per-stage spans.

Request latency is decoupled

The route commits the user message, creates a background task, registers it in a process-wide set, and returns. That is a good transport pattern.

Answer latency is not bounded by the 202

The background task still pays route resolution, permissions, context assembly, repeated model turns, tools, citations, suggestions, audit, usage, and commit.

Failure ownership moves too

Client timing must measure accepted → start → first visible answer → terminal, not only the POST response.

Progress events help—but do not shrink latency

Preparing/thinking/finalizing status is honest UX. It does not change first-answer-byte or total completion time.

Perceived chat latency

The answer stream is intentionally buffered until the whole turn finishes

async for event in gateway.stream_tools(...):
    if event.text:
        text_chunks.append(event.text)

return tool_calls, finish_reason, text_chunks

# caller, only after the turn returns:
await _publish_text(state, turn_text)

Result: a tool-free “streamed” answer does not become visible token-by-token. Chunks are flushed rapidly after the provider’s turn completes.

Why it was designed this way

The runtime cannot know early text is answer content until it knows the model will not issue a tool. Buffering prevents “I’ll search…” narration from being persisted as the final answer and keeps retries safe.

Performance consequence

Time-to-first-visible-answer approaches full model-turn time. On a slow/free route, the UI looks stalled even though upstream tokens are arriving.

This is a deliberate correctness/UX trade-off and needs an ADR-level redesign—not a one-line flush.

chat_runtime._stream_one_turn and _publish_text; gateway.stream_tools.

Realtime overhead

Every WebSocket envelope creates and closes a Redis client

async def publish(...):
  client = redis.from_url(...)
  try:
    async with client.pipeline() as pipe:
      RPUSH · LTRIM · EXPIRE · PUBLISH
      await pipe.execute()
  finally:
    await client.aclose()

Owner bind/read and subscriptions also create transient clients.

A single answer emits start, step events, narration, many deltas, citations, suggestions, and terminal state. Client lifecycle cost scales with envelope count.

Redis client churn ∝ streams × envelopes per stream

Low-load symptom vs scale blocker

This may not dominate one local answer, but it converts richer streaming into connection churn and adds tail variance exactly where the UX expects immediacy.

Use one application-lifetime pooled Redis client; keep per-stream pub/sub objects scoped.

backend/app/realtime/backplane.py.

Admission control

Answer production has lifecycle tracking—but no capacity gate

What exists

  • Process-wide task set.
  • Done callback removes tasks.
  • Shutdown cancels and drains with a grace timeout.
  • Tool fan-out semaphore.

What is missing

  • Global active-answer limit.
  • Per-tenant admission quota.
  • Queue depth and wait budget.
  • Overload response / retry-after.

Failure mode

Every accepted request can create another long-lived coroutine, runtime DB session, provider stream, Redis publisher, and tool batch. Saturation becomes latency collapse rather than controlled rejection.

stable service: arrival rate < sustainable completion rate — with a bounded queue

Priority: measure active answers and queue time first; then enforce capacity by deployment and tenant.

main.py and api/v1/chat.py; no answer semaphore/limiter found.

Large-object path

Uploads and inline previews buffer whole files in application memory

Upload

data = await file.read()
await object_store.put(..., Body=data)

Up to 50 MiB is materialized before validation/storage. Concurrent uploads multiply API memory and garbage-collection pressure.

Inline content

body = await stream.read()
return StreamingResponse(
  iter((content.data,)), ...)

The response is named “streaming,” but storage bytes were already fully buffered. Local config intentionally disables direct object-store redirect.

Why users notice

Large previews/uploads compete with the same process that handles auth, search orchestration, and chat admission.

Design direction

Stream/spool uploads with incremental size enforcement; use direct/presigned transfer or bounded chunked proxying for downloads.

Avoid false starts

What not to optimize first

Do not rewrite FastAPI

Liveness p50 is 2.6 ms. Framework replacement would not repair migration drift, Vite polling, external model latency, or buffered answer semantics.

Do not tune OpenSearch first

Idle OpenSearch CPU was ~1.5%; observed hybrid searches in task logs returned quickly after embedding. Measure query spans before index-level tuning.

Do not call dev-server timing “production”

The build preview is dramatically faster. Keep development experience and production delivery as separate SLOs.

Do not hide the bundle warning

Raising Rollup’s threshold changes no bytes and leaves a circular chunk-order warning unresolved.

Do not add retries blindly

Retries can turn transient faults into long queue occupation. Every retry needs a total deadline and admission budget.

Do not benchmark the current database

Its revision is incompatible with the current repository. First establish a clean, reproducible state.

Prioritization based on measured bottlenecks and invalid-state evidence.
