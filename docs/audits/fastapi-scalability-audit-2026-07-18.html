Executive verdict

Structurally strong; operationally unproven

The architecture is thoughtfully shaped for enterprise correctness. The dominant risks are not “rewrite the system” problems—they are concentrated capacity, lifecycle, and observability problems.

Do not claim production scalability yet

A Redis client is created per stream envelope, chat transactions can hold database connections across model/tool latency, and answer production has no global or tenant admission limit.

The foundation is worth preserving

Async adapters, RLS-backed tenancy, contract-first APIs, bounded public pagination, durable workers, typed errors, and extensive negative tests are all sound starting points.

Criterion 1 · Layering

Clear module ownership is weakened by transaction leakage

What is working

  • Vendor access is concentrated behind named adapters.
  • Domain modules are mostly pure and provider-agnostic.
  • Architecture tests enforce several sensitive import seams.
  • Routers consistently use service objects rather than raw clients.

What breaks the promised direction

  • 67 explicit commit/rollback calls appear across 17 router files.
  • Services and a task import SQLAlchemy/model types directly in 3 modules.
  • Request-scoped AsyncSession is exposed through service constructors.

Transaction ownership is part of architecture. When routers decide commits and services issue SQL, business use-cases cannot guarantee a single consistent unit of work.

router → use-case → repositories
one transaction boundary per use-case

Recommendation

Introduce application use-case functions that own session_scope, commits, rollbacks, and after-commit events. Keep repositories as the only SQL surface and return domain values—not sessions—to the API layer.

This is an incremental refactor. Start with chat/send, document upload, and admin mutations where transaction semantics affect reliability.

AGENTS.md §6; backend/AGENTS.md; backend/app/api/v1/*.py; backend/app/services/admin_service.py; audit_query_service.py; tasks/sync_source.py.

Criterion 2 · Async

The async model is sound, with one exploitable CPU exception

Good event-loop discipline

  • FastAPI, SQLAlchemy, Redis, HTTP, S3 and OpenSearch paths are async.
  • Celery broker publishing is explicitly moved through asyncio.to_thread.
  • CPU-heavy document parsing runs in Celery workers.
  • Parallel tool calls are capped per answer with a semaphore.
  • Ruff enables flake8-async; tracked code passes.

Blocking authentication path

AuthService.login() calls Argon2 password verification—and a dummy Argon2 verification for unknown users—directly inside an async request.

That protects against account enumeration, but CPU/memory-hard verification occupies the event-loop thread. A login flood can delay unrelated requests served by the same worker.

Fix: run verification in a bounded thread executor, cap concurrent verifications per process/tenant/IP, and rate-limit login attempts.
Secondary issue: several outbound adapters create short-lived HTTP clients per call. They are non-blocking, but repeated TLS/DNS/connection setup sacrifices pooling and increases tail latency.
backend/app/services/auth_service.py:99–146; backend/app/auth/hashing.py:24–61; backend/app/api/v1/chat.py:742–755; backend/pyproject.toml Ruff ASYNC rules.

Criterion 3 · Resource lifecycle

A new Redis client is built for every streamed envelope

Critical hot path

Streaming output multiplies connection-pool construction and teardown by the number of envelopes, not by the number of requests.

Impact under load

  • Redis handshake and pool churn on the highest-frequency path.
  • Extra sockets, allocations and garbage collection.
  • Tail latency grows with response length and concurrency.
  • Redis becomes a bottleneck before its command throughput is reached.

Remediation

Construct one process-wide Redis client/pool in lifespan, inject it into RedisBackplane, reuse it for publish/owner operations, and close once at shutdown. Preserve one dedicated pub/sub connection per subscription.

backend/app/realtime/backplane.py:156–271. OpenSearch and the SQLAlchemy engine already demonstrate the desired process-lifetime pattern.

Criterion 4 · Transactions

Chat holds a database transaction across model and tool latency

Open runtime sessionA fresh AsyncSession is created after the HTTP response.
Bind tenant / begin transactionSET LOCAL executes and checks out a connection.
Wait for LLM + toolsStreaming, provider failover, retrieval and tool turns happen before commit.
Persist answer + citations + auditAtomicity is strong, but the connection has already been occupied.
Commit onceThe transaction ends only after the whole answer succeeds.

The trade-off is currently too expensive

Atomic “all-or-nothing answer” persistence is valuable. It does not require holding the same database transaction open while waiting on external model and tool calls.

Target transaction shape

  1. Short transaction: authorize, persist user turn, reserve stream/run record.
  2. No DB transaction: call models and tools; use short isolated reads as needed.
  3. Short transaction: persist answer, citations, usage, terminal state and audit atomically.

If exact answer/audit atomicity across steps is required, specify it in an ADR and use explicit state transitions or an outbox—not an implicit long-lived ORM transaction.

backend/app/services/chat_runtime.py:434–520; bind_tenant executes before _answer; commit follows all external work.

Criteria 4–5 · Queries & bounds

Public pagination is disciplined; several consumers bypass it

Strong API behavior

  • Most list limits are validated in the 1–100 range.
  • Stable keyset cursors use timestamp + UUID tiebreakers.
  • Citation hydration has batch queries.
  • Chat context is token-bounded and summarized.

Unbounded internal paths

  • Pre-summary chat history can materialize a full session.
  • Enabled schedule reconciliation scans the fleet.
  • Pending-digest tenant discovery is unpaged.
  • Several per-resource repository lists have no explicit cap.

Frontend stops at page one

  • Document list does not consume next_cursor.
  • Chat sessions/messages request only the first page.
  • Search accepts a cursor in the API layer but has no navigation UI.
  • Tracked debt already exists in issues #274, #275 and #281.
Index concern: multiple keyset queries filter by tenant_id + owner_id and sort by created_at/updated_at + id, while their indexes often cover only the filter prefix. Validate with real PostgreSQL EXPLAIN (ANALYZE, BUFFERS) and add composite order-aligned indexes where proven.

Criteria 5 & 8 · Backpressure

Answer production is detached—and admitted without a ceiling

POST message
→
202 response
→
create_task()

Current behavior

  • Every accepted send creates an in-process asyncio.Task.
  • The process-wide task set is self-cleaning but unbounded.
  • No global, per-tenant or per-user concurrent-answer limit was found.
  • A WebSocket disconnect stops relay but intentionally does not stop model production.

Reconnection-friendly detached work is a reasonable product choice. Without admission control, it converts bursts into simultaneous DB, Redis and LLM pressure.

Required control plane

  1. Bound concurrent answers per API process.
  2. Enforce per-tenant/user quotas in Redis.
  3. Return 429/503 + Retry-After before work starts.
  4. Record queued/running/terminal state outside process memory.
  5. Make continue-on-disconnect explicit; cancel abandoned work when policy says so.
Do not use Celery blindly for token streaming. Preserve realtime latency, but put a bounded admission layer in front of the in-process producer.
backend/app/api/v1/chat.py:648–764; backend/app/main.py:75–125; realtime subscriber disconnect behavior in backend/app/api/v1/chat.py.

Criterion 9 · Payloads

The API “streams” only after loading the whole object

Upload path

data = await file.read()
...
validate_upload(size_bytes=len(data))
await client.put_object(Body=data)

The 50 MiB limit is checked after the router materializes the entire file. Content addressing hashes the same in-memory bytes. Concurrent uploads multiply memory pressure.

20 × 50 MiB = 1 GiB raw payload memory

Download path

response = await client.get_object(...)
body = await stream.read()
return StreamingResponse(iter((content.data,)))

The scale-safe path already exists: a presigned redirect is the configuration default. Local Compose overrides it to inline mode, which reads the object fully and yields one in-memory chunk.

Good seam: presigned GET and PUT methods exist in the storage adapter; the direct-upload PUT path is not yet used by the UI.
Fix: use direct-to-object-storage uploads or chunked reads with an enforced running byte cap; stream hashing; keep production downloads redirected/CDN-backed; bound any unavoidable proxy stream.

Criteria 6 & 11 · Background work

Celery semantics are thoughtful, but worker containment is incomplete

Strong worker design

  • JSON-only serialization; no pickle.
  • acks_late and prefetch = 1.
  • Idempotent state machines and bounded retry counters.
  • Redis-backed per-tenant rate limiters for outbound work.
  • Explicit event-loop lifecycle tests for repeated task execution.
  • Sandbox work is isolated behind a dedicated service.

Missing containment controls

  • No global soft/hard task time limits.
  • No task_reject_on_worker_lost setting.
  • No explicit Redis visibility timeout.
  • No worker concurrency, max-tasks, or max-memory policy.
  • Retry backoff is often deterministic, without jitter.

Delivery atomicity gap

Several API flows commit durable state and then publish to Celery best-effort. A broker failure can leave a committed row with no job unless a later reaper repairs it.

Fix: transactional outbox + dispatcher, or an explicitly proven reconciliation loop for each job type.

backend/app/tasks/celery_app.py; tasks/ingest.py; tasks/index_sync.py; tasks/rate_limit.py; tasks/run_assistant.py; docker-compose.yml:227–272.

Criterion 7 · Horizontal scale

The data plane scales out better than the work-control plane

Scale-out enablers

  • Postgres, OpenSearch, MinIO and Redis own durable/shared state.
  • Redis pub/sub supports cross-instance WebSocket delivery.
  • Replay is capped at 512 envelopes and expires after 15 minutes.
  • Stream owner bindings are externalized with TTL.
  • The API can be replicated without sticky HTTP sessions.

Replica-level gaps

  • Answer tasks and shutdown cancellation live only in one process.
  • No durable cross-replica answer queue/lease/cancel state.
  • Embedding cache is bounded but process-local and duplicated.
  • Each container entrypoint runs migrations; multi-replica startup would race.
  • Redis carries broker + realtime + rate limits, increasing blast radius.

Design implication

The API is close to stateless for request/response traffic, but detached chat work needs an explicit ownership model before replicas can be treated as interchangeable during deploys, crashes, and cancellation.

Criterion 10 · Caching

Caching is deliberate—and should stay measurement-led

Provider prompt cache

Stable per-session keys and cache-aware prompt layout preserve reusable prefixes. Usage extraction records cached and written token counts.

Embedding cache

Single-query embeddings use an opt-in, namespaced, hashed-key LRU + TTL. Capacity and TTL are bounded by settings.

Client cache

TanStack Query centralizes server-state caching and request cancellation for the SPA.

Gaps

  • Embedding cache duplicates across API/worker replicas.
  • Cache KPI is a structured log, not a queryable service metric.
  • No end-to-end cache hit, cost, latency or eviction SLO.
  • Redis is described as a cache but is used mostly for coordination/replay.

Do not add broad response caching to conceal slow queries. First fix transaction scope, resource reuse and query plans; then cache only stable, permission-safe data with explicit invalidation.

Security rule: every shared cache key must include tenant + authorization-relevant scope, or cache only post-permission public metadata.

Criterion 8 · Resilience

Timeouts exist; coordinated overload behavior does not

Good failure hygiene

  • LLM, MCP, web search, sandbox and broker paths have explicit timeouts.
  • Vendor failures map to typed internal problems.
  • Tool turns, tool concurrency, search results and replay are bounded.
  • Shutdown drains/cancels answer tasks under a grace window.

Readiness is incomplete

Postgres, Redis and MinIO are checked concurrently. OpenSearch—the required retrieval store—is omitted, and individual checks have no outer timeout budget.

Missing overload mechanisms

  • No Uvicorn limit-concurrency or backlog policy.
  • No global answer or database checkout budget.
  • No bulkheads separating chat, admin and health capacity.
  • No circuit breaker around failing providers/dependencies.
  • No standard 429/503 + Retry-After load-shed response.
  • No dependency latency/error metric to drive circuit decisions.
Principle: a scalable service must reject some work predictably before accepting more work than it can finish.
backend/app/api/health.py:63–129; backend/app/core/config.py timeout settings; backend/Dockerfile CMD; backend/app/main.py lifespan.

Exit criteria

Production readiness should be demonstrated with guardrails

Latency

  • REST p95/p99 by route class
  • WS first-token and total time
  • DB pool wait p95/p99
  • Redis publish p95/p99
  • LLM/tool dependency time

Saturation

  • Active/queued answers
  • Pool checked-out / overflow
  • Event-loop lag
  • Worker queue age and depth
  • Process memory under max uploads

Correct load shedding

  • Bounded 429/503 rates at capacity
  • Retry-After honored by client
  • No cross-tenant degradation
  • No orphaned answer/job state
  • Graceful rolling deploy drain

Suggested release gate—not a guessed SLO

Choose a representative concurrency and corpus, sustain it for 60 minutes, survive a dependency slowdown and one replica termination, remain within agreed p95/error/memory budgets, and produce enough telemetry to explain every controlled rejection.

Final numeric SLOs require product traffic assumptions and cost constraints. The audit intentionally avoids inventing them.

Decision

Keep the architecture.
Fix the hot paths.
Then measure the system.

Lumen Copilot does not need a framework rewrite—or a blanket DRY rewrite. It needs disciplined resource lifetimes, short database transactions, bounded admission, memory-safe transfer, observable load, and evidence-led cleanup of legacy seams.

Preserve

RLS, adapter chokepoints, contract-first design, typed errors, durable jobs, negative tests.

Fix first

Redis reuse, chat transactions, admission control, payload streaming, telemetry.

Prove next

Capacity, graceful shedding, failure recovery, safe dead-code removal, production deployment and cost.

Recommended decision: authorize the P0 hardening program before adding substantial new chat/tool workload.
