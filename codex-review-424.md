🤖 Codex CLI independent review (model gpt-5.6-sol, xhigh) — verdict: needs-changes

1. **major — `backend/app/services/chat_runtime.py:610`** — The budget is enforced only for the initial `[system, history, question]` prompt. Each tool-calling turn then appends an assistant tool-call message and the full `ToolResult.content` (`:575-595`), and both the next ordinary turn and the forced-synthesis call here reuse that growing list without recounting it. A long/repeated retrieval result or an unbounded MCP result can therefore overflow on the second/later call, so the advertised pre-call guarantee and typed-refusal behavior do not cover the forced-synthesis path. **Suggested fix:** carry the resolved budget/counter into the loop and validate every provider call, including forced synthesis; reserve and enforce a live-segment budget before appending tool results (using bounded evidence-preserving rendering/compaction), and add a regression test whose long tool transcript would otherwise exceed the window before synthesis.

2. **major — `backend/app/services/chat_runtime.py:549`** — `assembled.retrieval_k` is threaded only into `ToolContext.default_k`, which is a fallback rather than a cap: `search_text` still accepts an explicit model-supplied `k` up to 20 (`backend/app/services/tools/impls/retrieval.py:81`), while `search_documents` and `list_documents` use independent defaults. In addition, `ContextBudget.snippet_budget` is always `None` and is never passed to or enforced by any renderer. Thus the tight-budget `k=3` path does not reliably constrain retrieval before tools run, contrary to ADR-0016 §1. **Suggested fix:** derive hard per-run `max_k` and snippet/result budgets, add them to `ToolContext`, clamp every retrieval tool to those limits (including explicit `k`), and test the tight path end-to-end with explicit `k=20` plus the other retrieval tools.

3. **major — `backend/app/llm/context.py:198`** — The fixed-segment estimate does not count the serialized tool payload actually sent by the gateway. It concatenates only each tool's name, description, and parameter schema, omitting the per-tool `{"type":"function","function":{...}}` wrapper, keys, separators, and list framing constructed in `backend/app/llm/gateway.py:220-232`. With a sufficiently large MCP allow-list, that uncounted per-tool overhead can exceed the fixed 1,024-token safety margin, allowing a tools-only oversized prompt to reach the provider instead of raising `context_too_large`. **Suggested fix:** share a stable provider-neutral serialization/counting helper with the gateway (or use LiteLLM's tool-aware counter seam) so the exact full tool structures are counted, and add a tools-only boundary/refusal test with many small schemas.

4. **major — `backend/app/llm/context.py:138`** — The tokenizer-failure fallback `len(text) // 4` is an English-prose average, not a safe estimate. CJK, emoji, dense code, and JSON can consume roughly one or more tokens per character, so a large fixed prompt can be undercounted by several times; a fixed 1,024-token margin cannot absorb that error. This recreates the provider-side overflow that this PR is intended to prevent. **Suggested fix:** use a conservative model-independent upper bound (for example UTF-8 byte length) when the real tokenizer fails, and pin tokenizer-exception tests with multilingual/emoji fixed prompts that must refuse before the gateway call.

5. **minor — `backend/app/llm/context.py:130`** — Both lazy `import litellm` statements are outside their protective `try` blocks (the second is at `:145`). If import/initialization itself fails, the exception bypasses the promised heuristic/model-window fallback and becomes a terminal 500. **Suggested fix:** move each import inside the corresponding `try` and test an import failure as well as a `token_counter`/`get_model_info` call failure.

6. **minor — `backend/app/core/config.py:388`** — The new settings accept zero or negative fallback/headroom values. In particular, a negative `CONTEXT_OUTPUT_HEADROOM_TOKENS` silently increases the usable input budget beyond the model window, defeating the safety invariant instead of failing at startup. **Suggested fix:** validate the fallback as positive and headroom as non-negative (and reject an unusable fallback/headroom relationship), with Settings tests for the invalid values.
