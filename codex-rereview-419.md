This PR is already merged, so every finding below needs a follow-up PR.

1. **Major — `backend/app/services/chat_runtime.py:617` / `docs/architecture/0016-context-engine-and-cache-first-prompting.md:57` — the ledger records the requested model, not the model actually used.** `_answer()` resolves `route` once and sends `route.model` to every gateway call, but the new row is written with `model=model`. For a tenant provider route this persists `provider:<uuid>:<raw-id>` even though the upstream model was `<raw-id>`, directly contradicting ADR-0016 §2.6's requirement that each row carry the model *actually used*. That makes route-level cost/accounting aggregates wrong now and is incompatible with the ADR's retry/fallback attempt model. **Fix:** persist `route.model`; keep `route.api_key` and `route.api_base` out of the row. Add a routed-provider runtime test that supplies a public model id plus a `ModelRoute(raw_model, secret, base_url)` and asserts the row contains only `raw_model` (never the key or URL). Update `backend/tests/test_chat_runtime.py:990`, which currently locks in only the passthrough case.

2. **Moderate — `backend/app/services/chat_runtime.py:165` — `done.usage` can still violate the contract's `minimum: 0`.** `_as_count` correctly sanitizes LiteLLM/vendor values, but `TokenUsage` itself accepts arbitrary integers and `_Usage.add()` blindly adds them. A scripted/future adapter yielding `TokenUsage(prompt_tokens=-1, ...)` therefore produces a negative `done` field while `LlmUsageRepository.record()` clamps the persisted row to zero; the wire contract is broken and the two accounting views disagree. **Fix:** enforce non-negative `TokenUsage` values at the domain boundary or clamp each field in `_Usage.add()`, then add a runtime-level negative-usage test that validates the emitted envelope and stored row agree.

3. **Moderate (test gap) — `backend/app/services/assistant_test_service.py:273` — preview rollback of `llm_usage` is correct today but has no executable guard.** The shared-session rollback does discard the row because the insert is in `_answer()` on that same session, but the harness comment enumerates chat sessions/messages/citations/audit only, and no assistant-test assertion checks that `llm_usage` remains empty. This is a load-bearing side-effect-free guarantee under the repo's prose↔mechanism rule; a later move to a separate accounting session would regress silently. **Fix:** extend an assistant-test service/API test to query `llm_usage` after the preview and assert zero tenant rows, and update the rollback comment.

4. **Low (test gap) — `backend/tests/test_chat_runtime.py:914` — two answer branches are not pinned for accounting.** The multi-turn test covers a tool turn followed by a natural answer, and the zero-usage test covers a normal answer, but neither proves usage from the forced-synthesis call is included nor that the `NO_SOURCES_FALLBACK` path still writes exactly one row. The current placement after both branches is correct, but it is unprotected. **Fix:** add forced-synthesis and empty-synthesis/fallback cases asserting both `done.usage` and the single persisted row.

5. **Nit — `backend/app/services/chat_runtime.py:611` — the mitigation left a stale deferred-FK explanation.** The migration and ORM now correctly use an ordinary immediate FK, but this comment still says "the deferred FK validates at commit." **Fix:** state that `_persist()` has already flushed the message, so the immediate FK is satisfied in the same transaction.
